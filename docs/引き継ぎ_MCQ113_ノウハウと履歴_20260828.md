# 5. 設計の要点（外してはいけない線）

## 5-1. 「評価」ではなく「指針」、「評価する」ではなく「承認する」

- サンクスUP！96項目 ＝ **評価基準**。2026年3月にみんなで作成し内容はOK。
  **細かい文言と最終承認はまだ。運用も走っていない。**
- 全体マンダラ64 ＝ **経営計画から降りてきた指針**。**未承認の提案段階。**
- 「そのとおりにやったら**承認**します」という言い方にする。
- **評価で行動を縛るとびびってしまう**（松山）。これが理由。

## 5-2. サンクスUP！96はマンダラに載せない

96項目は**評価基準（＝咲いた花を調べる図鑑）**であって、毎日見る目標ではない。
マンダラに載るのは**経営計画から降りる項目**。
（96は9×9＝81マスに収まらない、という技術的理由も併存するが、本質は上）

## 5-3. 3層のマンダラ、3ヶ月ごとに見直す

```
経営理念・フィロソフィ51
      ↓
   経営計画（3ヶ月ごとに置き直す）
      ↓ 降ろす
会社全体のマンダラ ／ 部署のマンダラ ／ 個人のマンダラ（OKR）
      ↑ 光の粒が積み上がる        ↑ 毎週の中身＝GCシート
             日報（書くのはここだけ）
```

⭐ **個人のマンダラOKRの「毎週の中身」は、すでに動いている週次GCシートが担う。新しいシートは作らない。**
石川さんの「余計な仕事を増やさないで」はここ。
（五十嵐商会の「チャレンジシート」＝重点取り組み課題は個人マンダラに含まれるもの。高村さまのGCシートは
軌道修正を毎週流すもので、マンダラOKRと役割が同じ）

## 5-4. AIは点数を付けない

契約第9条3項。**材料を揃えるところまで。**
目指すのは「印象を置き換える」ではなく「**印象に根拠を足す**」。

## 5-5. EXP（光の粒）は人事評価に使わない

日々の励みのためのもの。人事評価に持ち込むと日報が点数稼ぎに歪む。
GCシート・チャレンジシートにもEXPは出さない（内省の場に点数を持ち込まない）。

## 5-6. 機械が書かない欄は、意図して空ける

GCシート13欄のうち**7欄が自動、6欄は空欄**。
空ける6欄＝外的な変化／内的な変化／効果的な計画／ドラッカーのコンセプト／
フィロソフィ目標／フィードバックコメント。
「AIに任せる」ではなく「**気づきを与える素材**」として出す。書く時間を省いた分を対話に注ぐ。

## 5-7. 成果6分類の構造

①直接の成果（会計）②直接の成果（業務）③価値への取り組み ④人材育成 ⑤チームへの貢献
⑥他チームからの貢献を引き出す

⭐ **①②③④は「やったことの種類」で決まる（96項目で機械的）。
⑤⑥は「相手が誰か」で決まる（日報本文を読むしかない）。** 直交する軸。
だから96項目に⑥に当たる項目は0件になる。これは間違いではない。

## 5-8. 評価ツール4点との接続（8/28判明）

石川さまが見ている一気通貫の終点は**人事評価（賞与・昇格）**。契約書の表題もそちら。

⭐ **人事評価集計表の配点は 能力30／行動60／業績10 ＝ 100点。**
行動60点の内訳6項目（真面目に一生懸命・感謝の気持ち・常に明るく・正直である・
ベクトルをあわせる・フィロソフィ目標）が、**行動基準のフィロソフィ**と
**評価表のフィロソフィ評価欄**と**完全に一致**している。

→ **日報解析がいちばん効く場所は、GCシートではなく「評価表の行動欄」。**
配点の6割が、いまは記憶と印象で決まっている。ここに1年分の実例を根拠として付けられる。

| 評価ツール | 接続 |
|---|---|
| 行動基準（フィロソフィ基準） | ⭕ 繋がる。着眼点の全文があれば対応表を作れる |
| 評価表 | 🔺 根拠資料まで。点数は人が打つ |
| 資格等級基準・専門能力基準 | ❌ 日報では判定しない。Stageは「物差し」として添える |
| 人事評価集計表 | ❌ 集計の器。数字は人が入れる |

**社員番号が、日報解析と評価ツールを繋ぐ唯一のキー。**
`TK_MEMBER_HEADER` の**末尾**に `社員番号` を追加済み（既存の列番号がずれない）。
移行関数 `tkメンバー表_社員番号列を追加()`、メニュー⑧-。

| poppler（pdftoppm） | **pymupdf（fitz）** でPDF→PNG |
| clasp | **貼付方式のみ**（takamura-sunsun.com の再認証ポリシー `invalid_rapt`） |
| pptxgenjs（未インストール） | **python-pptx** |

使えるもの：**ffmpeg 8.1.1** ／ **edge-tts** ／ python-pptx ／ python-docx ／ reportlab ／ Pillow ／ Chrome

## 6-2. Bashヒアドキュメントがバックスラッシュを食う（何度も踏んだ）

`<<'EOF'` の**クォート付きでも** `\\n` が `\n` に、`\n` が実改行になる。
結果、生成したJS/Pythonの文字列リテラルが壊れる。

**対策**
- ヒアドキュメント内には**バックスラッシュを一切書かない**
- Windowsパスは `C:/Users/...` と**フォワードスラッシュ**で書く
- 改行が要るときは `chr(10)` や配列の `join` を使う
- 大きいコードは**Writeツールでファイルに書く**（heredocを使わない）

## 6-3. python-pptx

- 🔴 **日本語フォントは `font.name` だけでは効かない。** `a:ea` / `a:cs` を lxml で明示する。
  入れないとPowerPointで別フォントに化ける（`_ea()` ヘルパー）
- 影は必ず `shape.shadow.inherit = False`（既定で影が付く）
- ハイパーリンクは run 単位：`run.hyperlink.address = url`
- 🔴 **スライドの自動送り（動画化）はAPIがない。XMLを直接入れる。**
  `<p:transition spd="slow" advTm="7000"><p:fade/></p:transition>` を `p:sld` の子に。
  **要素順が厳格**：`p:cSld` → `p:clrMapOvr` → `p:transition` → `p:timing`。
  並べ替えないとPowerPointが修復扱いにする
- ナレーションは `slide.notes_slide.notes_text_frame.text`
- **JPEGでは透過が消える。** 円形画像はPNGで、さらに256色に減色して軽くする

## 6-4. HTML→PDF（Chrome headless）

```
chrome --headless=new --disable-gpu --no-pdf-header-footer --virtual-time-budget=6000 --print-to-pdf=out.pdf file:///<絶対パス>.html
```

- 🔴 **A4固定は `.page{height:297mm; display:flex; flex-direction:column}`。**
  `min-height` ＋ フッター `position:absolute` にすると、わずかな溢れでフッターが次ページへ押し出され、
  4ページのつもりが8ページに割れる
- フッターは `margin-top:auto` の**最終子要素**にする
- `.page > * { flex-shrink: 0 }` を入れないと中身が潰される
- 検証は **pymupdf**：ページ数／最大y（<842pt）／各ページのフッター有無

## 6-5. HTML→スライド画像（Chrome headless）

```
chrome --headless=new --hide-scrollbars --force-device-scale-factor=1 --window-size=1920,<1080*枚数> --screenshot=all.png file:///...
```
→ PILで1080pxごとに切り分ける。**1回の起動で全枚数を撮れる。**

- PPTXと同じ座標系で組める：**1インチ＝144px、1pt＝2px**（13.333in → 1920px）
- LibreOfficeが無くてもこれで「PPTXと同じ見た目」の画像が作れる

## 6-6. 動画（MP4）を直接作る

```
① edge-tts で音声   ja-JP-NanamiNeural / rate -6%
② Chrome でフレーム画像
③ ffmpeg で結合
```

- 🔴 **スライドの尺は「実際の音声長」から決める。**
  文字数からの推定（6.3字/秒）は甘い。**実測は約4.5字/秒**。
  推定110秒が実測236秒になった。`slide = 0.5 + 音声長 + 1.1`（最低5秒）
- 音声は `adelay` で頭に間を作り、`apad` ＋ `-t` で尺ぴったりに切る。これで画と音がズレない
- 🔴 **ffmpegのconcat demuxerは最後のファイルをもう一度書く**必要がある（最終尺が出ない）
- 検証：各シーンの中央でフレームを抜き、元画像との差分を測る（0.005以下ならOK）
  ＋ `volumedetect` で無音・クリップを確認

## 6-7. 円形イラストの透過（フチの処理）

生成AIの円形イラストは**四角いクリーム地の上に円**が描かれている。そのまま貼ると四角い枠が見える。

- 円の位置は**決め打ちしない**。四隅8×8の平均を地の色とし、中央行・中央列を走査して端を検出
  （実測で円は枠の96〜99%に内接していた）
- マスクは**4倍に拡大して描いてから縮小**＝縁がなめらか
- **円形のときは枠線を描かない**（絵に金色のリングがあるので二重になる）
- スクリプト：`_画像_円形マスク_20260828.py`

## 6-8. 画像生成（ChatGPT）のプロンプト

- **【共通スタイル】ブロックを毎回先頭に貼る**のが画風統一の要
- **文字は描かせない。** 日本語は崩れる。文字は後でパワポ/HTMLで組む
- **1枚目を作ってから添付して「この絵と同じ画風で」**と続けると揃う
- ⭐ **連続する絵（成長3段階など）は「同じ鉢・同じ角度・同じ背景。咲き具合だけを変える」と明示し、
  1枚目を添付して2・3枚目を作らせる。** これで完全に揃った
- ⚠ **納品場所は指定どおりに来ないことがある。** `outputs/` と案内したが `画像_BQ版/` に置かれていた。両方見る

## 6-9. Gemini無料枠

**20 requests/day（RPMではなくRPD）。**
→ `TK.CLASSIFY_ON_SUBMIT: false`（送信時判定をやめる）＋ 1時間ごとに15件ずつのキャッチアップ。
429を受けたら記録せずに中断。3回連続で進捗0なら自動停止。

## 6-10. GASの落とし穴

- `tkEnsureSheet_` は**シート新規作成時にしかヘッダーを書かない**。
  既存シートに列を足すには**移行関数を別に用意する**（`tkクエスト表_GC分類列を追加()` など）
- 列の追加は**末尾に足す**。既存の列番号がひとつもずれない
- 一括処理で全幅 `setValues` するときは、**追加列の既存値を読んで書き戻す**（消える）
- `TK.SS_ID` はスタンドアロン導入では**必須**（時間トリガーがSS解決に使う）。バインド導入では逆に空に

## 7-1. 🔴 謝罪・自責を書かない。契約に影響する

- ❌「守れていません」「申し訳ありません」「ご迷惑をおかけし」「こちらの段取りの問題です」

- ⭕ ステータス語は 方針変更／方式変更／組み替え／設置後／◯月提示
  （**未了・未開始・未着手 を使わない**）
- ⭕ **対応状況の説明そのものはよい。** 遅れている事実は書く。そこに自責を足さない
- ⭕ 計画が変わったときは「**誰の・いつの決定で変わったか**」を主語にする

## 7-2. 🔴 発見物語にしない。見出しにニュース性を出さない

- ❌「日報は、すでに毎日書かれていました」「◯◯だと判明」「今月いちばん大きな発見」
- ❌「分かりました」「ここを我々は見ていませんでした」「ご指摘のおかげで」
- ⭕ 事実として淡々と書く。我々の結論は「◯◯に置き直します」と**こちらの行動**として書く

## 7-3. 存在しない契約違反を自分から作らない

契約条項を根拠に自責を書くときは、**その条項の頻度と前回提出日を必ず先に確認する**。

## 7-4. URLは装飾しない

`**` やカッコで囲むとクリックで飛べなくなる。**素のまま1行で置く。**

## 7-5. 書き終えたらgrepする

`申し訳 ／ ご迷惑 ／ 守れて ／ やり直 ／ 未了 ／ 未開始 ／ 未着手 ／ 間違い ／ 判明 ／ 発見 ／ 分かりました`
